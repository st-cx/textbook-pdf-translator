# 翻译并发与多个供应商

桌面入口的“翻译并发”可输入1–32，默认32；开始后设置冻结，安全停止后可修改再继续。自动模式的每批任务数默认跟随该数值。调度使用同一任务库，只处理当前尚未完成且来源允许的任务。

供应商池让多条已配置路线分担翻译。它只使用明确列入池的供应商，不会自行访问模型清单里的其他服务。网关模型ID是路由名称，不能单凭名称认定实际模型身份、价格或独立配额。

## 配置示例

在本地 `config.json` 中填写自己的服务地址、密钥和模型。可参考根目录的 [config.example.json](../config.example.json)。下面字段展示池的关系，实际供应商仍放在 `providers` 中：

```json
{
  "_default": "translation-pool",
  "_review_default": "example-review",
  "provider_pools": {
    "translation-pool": {
      "providers": ["example", "example-backup"]
    }
  }
}
```

每个池包含1–16个已有供应商名称，不能重复、嵌套，池名不能与供应商重名。翻译下拉同时列出池与单个供应商；选择单个供应商时只走该路线。复核下拉只列出单个供应商，可独立手选。

供应商可增加以下限制；未填写时每分钟60次、单路线最多32个在途翻译任务：

```json
{
  "requests_per_minute": 60,
  "max_concurrency": 8,
  "max_attempts": 2,
  "rate_limit_group": "shared-account-quota"
}
```

`requests_per_minute` 与 `max_concurrency` 是上限，按实际账号额度填写。相同服务地址、密钥、模型的别名自动共用时钟和容量；同账号中不同模型共享配额时，给它们填写相同 `rate_limit_group`。组内采用最严格的请求频率和容量。别名的不同组名不能把同一路线变成更多配额。使用自动路由别名时，应把可能共享上游配额的路线归入同组。

## 限流、失败与续传

- HTTP 429遵守 `Retry-After`，并以共享配额组冷却；没有该字段时采用有界退避。可用的其他组继续处理。
- 超时、连接失败和服务端错误会冷却并尝试其他路线；请求次数有上限，不会无限轮转。
- HTTP 400、401、402、403、404、405、415、422在本轮停用对应路线；账号额度及权限错误同时停用同配额组。其他可用路线继续。
- 池内全部路线不可用时，未完成任务保留待续传；已保存的有效段落不重发。恢复服务后重新开始会建立新的路由会话。
- 断点、部分提交、公式标记、数字、来源版本、租约及语义退回检查继续有效。历史永久失败需按原工作流程定位修复，不会被自动清空。

每一批复用同一限速和健康记录；抽查阶段沿用共享配额时钟，避免在已知冷却窗口内立即访问同账号。抽查仍使用独立选择的模型，不对整本逐句复核作完成承诺。

请求用量和译文来源记录实际供应商；部分回复由不同路线补齐时分别保留归属。未知价格的估算零值不表示免费。

## 验证范围

离线行为测试用真实任务库和模拟API验证64个任务的32、16、4并发峰值、后续批次、显式批量上限、故障切换、共享别名配额、部分提交及恢复。真实路线只使用少量自创短句验证可达性和结构协议。这些检查不能证明某个供应商持续支持32在途、全书耗时或数学语义已经验收。
